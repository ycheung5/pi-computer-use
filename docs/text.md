# Text and key entry

The candidate acquires [exclusive control](spec.md#exclusive-control) before physical text entry. Suppressed physical events do not invalidate typing; foreign injected or unconsumed events still do. Remaining Pi chord/focus/handback acceptance stays in #26/#31; native Pi-host Esc has an accepted receipt.

`type_text` accepts `text`, `method: auto | clipboard | sendinput | background`, `focusMode: preserve | main`, `restoreClipboard` (default true), and native target options. Browser options retain browser-first routing. `keypress` accepts a `keys` array with exactly one non-modifier key and optional Ctrl/Alt/Shift modifiers. Windows/Cmd/Meta keys are blocked; unsupported names/layout mappings fail without input. Explicit background keypress supports one printable character only.

Auto text first tries the focused native Edit/RichEdit control using bounded `EM_REPLACESEL`, preserving its selection. This quiet path handles Unicode without clipboard or physical keys; multiline text, main-focus selection and unsupported controls require physical entry. An uncertain edit-message result is never retried as clipboard input. Background WM_CHAR delivery is explicitly unverified. Read-only/disabled controls refuse mutation.

The operation's last target is reused after foreground restoration. Fresh Win32 focus takes precedence over remembered native focus. Only an agent-established focus is remembered; subsequent click/focus/target changes invalidate it. Remembered controls must retain their HWND/PID/root and unchanged input-history stamp. An intervening user input with unavailable fresh focus returns `TARGET_FOCUS_CHANGED`; it does not guess the old field. Main focus explicitly chooses the largest enabled, keyboard-focusable, on-screen writable Edit/Document control. Optional native edit `verifyValue` is capped at 200 characters and excludes password edits. Physical entry does not read password values.

## Physical entry and cleanup

Explicit `sendinput` text uses KEYEVENTF_UNICODE down/up pairs for ordinary text, Enter key pairs for LF or CR (CRLF becomes one Enter), and Tab key pairs for tabs. Whitespace-only strings are valid text. These keys retain the target application's normal Enter/Tab behavior. A cancellable 50 ms gap follows each dispatched unit: both unpaced delivery and a 10 ms gap were observed to corrupt appended text in modern Notepad despite successful dispatch. The pinned DSH reference instead batches Unicode events without this per-character delay. Pacing and control-character handling changed together in Pi, so the successful regression does not establish that 50 ms is necessary or isolate the cause. See the [Pi text validation scope](validation.md#unicode-mechanism-investigation). Minimum-delay discovery and DSH batching experiments are not release gates. This provisional compatibility workaround adds approximately 50 ms per unit plus platform scheduling overhead; it is not a universal guarantee about application processing. Dispatch remains unverified until a subsequent observation confirms the intended text. Successful results expose `inputDelayMs` so callers can identify the pacing actually used by the running helper. Default `auto` entry retains its existing quiet-edit/clipboard routing. Chords are mapped using the target thread's keyboard layout and use SendInput rather than an uninterruptible SendKeys call. The shared activity observer spans the whole call and distinguishes our tagged key events from intervening physical/foreign injected input; a later synthetic key cannot erase earlier intervention evidence. The helper rechecks target HWND/PID, foreground and cancellation before each character/key; text also checks focused control and user-held modifiers/buttons. Every held key/modifier is released in `finally`, even when its key-down result was uncertain. Partial text, timeout and cancellation never authorize automatic replay.

The independent stop event and retained-input acknowledgment from [pointer stopping](pointer.md) cover keyboard actions too. A timeout signals the operation to stop; missing release/clipboard acknowledgment retains ownership and blocks worker termination/replacement. `set_value` may escalate only an explicit background `WCU_NEEDS_INPUT`, after re-resolving the observed control, checking enabled/read-only state and focusing it; select-all and typing use the same guarded cleanup.

## Clipboard transaction

Clipboard entry uses a separate STA process with a hidden message-only owner window and message pumping. All UIA focus work finishes before clipboard replacement; restoration never calls application rendering providers. The snapshot phase duplicates each available public clipboard format, including native bitmap/metafile formats, using [OleDuplicateData](https://learn.microsoft.com/en-us/windows/win32/api/ole2/nf-ole2-oleduplicatedata). When OLE transport markers (`DataObject` / `Ole Private Data`) are present, the helper validates the advertised FORMATETC descriptors before omitting those process-bound markers. Public formats must be unindexed content, without a target device, and available in supported native storage. All public native payloads are still duplicated. Unmaterializable, genuinely indexed, device-specific or unsupported OLE data fails before replacement rather than falling back to text-only preservation. Snapshot/rendering has a five-second process deadline while mutation is still forbidden.

Only a completed snapshot permits replacement. The helper publishes zero-valued history/cloud exclusion formats before Unicode text, following [Microsoft's clipboard format contract](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats#cloud-clipboard-and-clipboard-history-formats). Clipboard sequence checks protect an intervening user copy. Windows can also advance the sequence while synthesizing formats during paste; restoration across that change requires both the helper's hidden owner window and its unique transaction nonce. A different owner or missing nonce preserves the newer clipboard instead. Ctrl+V is followed by a cancellable bounded wait and native WM_NULL drain; a stalled target returns an uncertain-dispatch error. The original opaque snapshot is restored in `finally` before cleanup acknowledgment, or the explicit `restoreClipboard: false` result keeps the injected clipboard content. Cancellation/error always requests restoration. A newer user copy is preserved.

Cancellation, parent exit or a 30-second stalled transaction also triggers independent restoration. OpenClipboard acquisition has bounded retries. If another application indefinitely holds the clipboard or restoration fails, the helper retains duplicate originals, retries restoration and leaves cleanup/ownership unconfirmed. It is never force-killed after mutation or silently reported restored. This is a fail-closed recovery condition, not a guarantee that Windows will release another application's clipboard lock.

## Validation and pending acceptance

- `npm test`: normal worker validation for text options, malformed/ambiguous chords, Windows-key blocking and unsupported background chords, plus shared stop/non-replay lifecycle tests.
- `npm run test:native:text` after build: background Unicode/emoji, remembered target, WM_CHAR, read-only and wrong-target refusal on disposable forms. Native auto-edit checks use the backend's ordinary quiet-attempt protocol, so failure cannot escalate into physical input. This is backend-seam proof, not full Pi auto-escalation acceptance. The suite never reads or replaces the clipboard and sends no physical keys/mouse input.
- The legacy `test:native:text:physical` runner refuses execution because it overwrote clipboard contents and could retire an unsettled input owner. Use the [existing OLE fixture](#ole-clipboard-regression) for its supported preservation cases; exclusive-control acceptance follows the delivery plan.

Physical paste, rich clipboard restoration, history/cloud behavior, synthetic Esc handling, real Esc stopping, password entry and restoration after menus/dialogs remain dedicated/manual acceptance checks. Check unsupported delayed/indexed formats fail without mutation and a locked clipboard fails without input. Exclusive-control acceptance requires physical user input to be suppressed during control and normal editing/copy to work after handback with its state preserved. Clipboard writes by other applications still require newer-copy protection. Stopped text is not replayed until a new user operation. The shared [coverage plan](implementation-plan.md#coverage-matrix) remains authoritative for release evidence.

Restoration acceptance (pending): during exclusive control, attempted physical typing, pointer movement and window selection must not change the owned task. After explicit handback, select a sibling window and edit/copy normally; verify no pending agent action or restoration overrides that user state. Explicit continuation must revalidate and reacquire control. External/programmatic focus changes still require target checks; field containment alone does not establish an agent-owned pointer move.

## Notepad Unicode regression

The runner requires fresh, independently observed window/process/thread identity, foreground, keyboard layout and focus within the UIA-observed editor HWND before Ctrl+End and again before test text. The editor HWND must be a distinct child of the owned root; a missing or virtual-only HWND stops the run as inconclusive. `--report-environment=/path/to/report.json` checks saved `{target, editor, observation}` evidence offline; a nonzero exit denotes incomplete evidence. The observation does not establish TSF/IME status or prove the target remains unchanged afterward. A subsequent paired Notepad append case validated these checks on both engines; Pi matched the expected text and the reference returned corrupted appended text. See [the scoped evidence](validation.md#unicode-append-with-verified-editor-focus).

List the six cases from WSL with `npm run test:native:notepad:unicode -- --list`; listing starts no backend or Windows application. On an authorized idle Windows desktop, build and run the default Pi engine with Windows Node and `PI_CU_NOTEPAD_INPUT_TEST=1`. Reuse the existing six-case and append passes; run only a missing or affected Pi case. The owned-document oracle compares exact UIA values and saved UTF-8 bytes, normalizing only line endings, and records method/timing plus observable editor/focus/keyboard context. Unknown IME/TSF state remains unknown; exhaustive instrumentation is not required. It saves/closes only owned test tabs after action-matched cleanup; uncertainty retains actual owners without replay. This does not by itself establish chord, handback or general activation acceptance. DSH runs are discarded under [ADR 0004](adr/0004-pi-first-acceptance.md); old paired receipts remain in validation.

## OLE clipboard regression

Preparation is portable and performs no clipboard or native actions:

```sh
npm run test:native:clipboard:plan

```

Use the existing runner with `--engine pi` (default). `--list-cases` and `--plan` report prepared cases without importing a backend or creating/launching Windows fixtures. Real execution requires Windows Node, a built Pi worker and `PI_CU_CLIPBOARD_INPUT_TEST=1` on an authorized idle desktop. Keep preservation/cleanup gates before clipboard mutation. The legacy reference-engine option is historical and is not required or scheduled for acceptance.

For a future explicitly enabled run, the fixture privately caches the original text/stream clipboard formats and restores only when it still owns the seeded clipboard; a genuinely intervening copy is preserved. Unsupported original fixture formats are refused before seeding. No clipboard payload is printed. The same fixture checks actual editor text independently against UIA, synthetic Unicode/HTML/binary preservation, indexed-OLE payload preservation and synthetic newer-copy preservation. An indexed attempt may refuse without input or report exact paste with preservation; the report records which occurred rather than requiring DSH to use Pi’s refusal policy. Raw tool results/errors and any optional cleanup diagnostics remain in the output; Pi-specific restoration labels/counts are not required from DSH. An explicitly unconfirmed cleanup blocks subsequent cases. Only owned fixture files/processes are eligible for cleanup; normal applications and documents are untouched.

Historical reference-client activation/cleanup constraints belong to the retained comparison evidence. Current Pi acceptance requires action-matched cleanup, independent clipboard/editor observations and retention of uncertain owners; no reference backend is needed.

The safe CLI checks establish preparation and gating only. Windows C# compile-only validation passed for the modified clipboard fixture without executing it or accessing the clipboard. Dedicated runs verified supported paste/restoration and newer-copy preservation for Pi; DSH lost the synthetic newer copy. A standard virtual-file case independently verified indexed data before and after each tool call: Pi refused safely and preserved it, while DSH reported dispatch but the indexed content was no longer retrievable. Plain-only clipboard, locked/delayed content, additional rich formats, history/cloud exclusion and remote desktop behavior still require additional dedicated acceptance; this runner does not claim that coverage.

Pi publishes zero-valued `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory` and `CanUploadToCloudClipboard` markers for temporary clipboard text. Actual supported Windows behavior and locked/delayed-backend acceptance remain #27 work; source flags alone do not establish every service behavior.

Clipboard results expose `clipboardSnapshot` counts (`preservedFormats`, `oleMetadataExcluded`, `oleFormatsValidated`) and `clipboardRestoreOutcome`: `restored`, `newer-copy-preserved`, `kept`, or `unchanged` when no replacement was authorized. Cleanup confirmation alone is not a claim that the original clipboard was restored. OLE transport markers are regenerated by Windows/consumers as needed rather than restoring stale interface handles.

Physical comparison diagnostics can select one fresh Unicode case with `--case=3` (IDs 1–6); `--list --case=3` safely reports the selected seed and text. The opt-in runner also offers isolated, labeled `--diagnostic=pi-no-delay`, `--diagnostic=reference-keyup-scan`, and `--diagnostic=reference-pair-batches` variants, each changing one variable in a temporary copy and recording hashes. These are diagnostic experiments, not production settings. The read-only target-thread legacy context probe records raw API returns and leaves focused-context, open-state and TSF claims unknown unless independently established. A failed full run remains recorded; selecting a different case creates fresh state rather than retrying the failed action. The clipboard runner independently reads the indexed fixture payload before dispatch, so a malformed seed is distinguished from post-action corruption.

### Isolated clipboard diagnostics

Use `--case ole-preservation`, `--case indexed-refusal`, `--case virtual-file` or `--case newer-copy` with the existing runner to select one case. `--plan` still works from WSL without desktop resources or opt-in. Each executed case resets only its fixture editor, verifies it is blank, seeds its own clipboard prerequisite and checks that seed before the tool call. Thus newer-copy can start independently from a fresh fixture; it does not depend on a successful indexed case or reuse an uncertain prior action.

`--probe-indexed` is a fixture-only diagnostic behind the same `PI_CU_CLIPBOARD_INPUT_TEST=1` gate. It temporarily replaces the clipboard but sends no keyboard/pointer input and starts no Pi/DSH backend. It compares the existing indexed data object directly with the object returned by `OleGetClipboard`, recording Query/Get results and their FORMATETC enumerations, then restores the original clipboard according to fixture ownership. A direct pass plus clipboard-query failure isolates the boundary; it does not establish why that boundary failed or justify a production change. This diagnostic leaves the indexed format unchanged. Startup refusal reports only a fixed category and HRESULT, never original clipboard formats or values. Before a valid HWND is returned no seed/backend command is sent; an early-exited fixture receives no cleanup command. Replies and stuck-startup retirement are bounded, and cleanup failures do not replace the original diagnostic. The [Shell clipboard contract](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard) documents indexed virtual-file `FileContents` with its descriptor as a separate supported design, which was tested separately as described in [the current evidence](validation.md#unicode-mechanism-probes-and-clipboard-startup--follow-up).

Portable selector/probe contracts were observed failing before these CLI options existed, then passing. The custom indexed fixture remains invalid through `OleGetClipboard`. The independently readable standard virtual-file fixture has since been executed against both engines; its results are recorded in the current evidence.

`--probe-locked` is a separate fixture-only prerequisite for future locked-clipboard comparisons. Its plan can be inspected on WSL with `npm run test:native:clipboard:ole -- --plan --probe-locked`. Execution uses the same dedicated-desktop opt-in, but does not start an engine, send input, read clipboard content or replace it. An owned fixture temporarily opens the clipboard; the OS-reported lock holder and a second process independently verify available → busy → available, and the clipboard sequence must stay unchanged. A fixture-side watchdog releases the lock after five seconds if the runner stops responding. This prepares a controllable contention fixture; it does not yet test Pi or DSH behavior while the clipboard is locked. On 2026-10-30, the dedicated fixture-only probe confirmed available → busy → available, matched the OS lock owner, left the clipboard sequence unchanged, and confirmed fixture cleanup. No clipboard contents were read or replaced and no Pi/DSH tool call was made. Locked-backend behavior remains untested.

Windows-only, no-input process probes support future timeout research: `npm run test:native:owner-supervisor` runs synthetic child processes, and `npm run test:native:owner-backend-health -- <reference-checkout>` calls only Pi and DSH health. Each starts its disposable runner suspended, assigns it to a Windows job before resuming, terminates the job on its test deadline and requires the job to report no active processes. The synthetic probe also checks that its descendant started and did not perform a delayed write. The health probe on a staged build returned healthy results and zero active job processes after retirement for both engines. The outer runner does not force a timeout: unconfirmed supervisor cleanup can wait indefinitely and retains its workspace. `npm run test:native:owner-crash-boundary` checks synthetic processes when their job owner is forcibly terminated: it verifies the two observed job members exit, while a separately brokered child outside the job survives and must be stopped separately. A normal synthetic control runs its managed `finally` block; the killed job worker entered its `try` block but did not run that `finally`. This establishes a containment and cleanup limit, not whether Pi or DSH uses such a broker or what happened to OS input state. These tests do not establish complete descendant containment, clipboard-lock continuity or physical input release. In particular, this supervisor is not a safe mechanism for terminating a possible physical-input owner and must not be used as a locked-clipboard acceptance run.
