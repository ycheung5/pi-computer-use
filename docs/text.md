# Text and key entry

`type_text` accepts `text`, `method: auto | clipboard | sendinput | background`, `focusMode: preserve | main`, `restoreClipboard` (default true), and native target options. Browser options retain browser-first routing. `keypress` accepts a `keys` array with exactly one non-modifier key and optional Ctrl/Alt/Shift modifiers. Windows/Cmd/Meta keys are blocked; unsupported names/layout mappings fail without input. Explicit background keypress supports one printable character only.

Auto text first tries the focused native Edit/RichEdit control using bounded `EM_REPLACESEL`, preserving its selection. This quiet path handles Unicode without clipboard or physical keys; multiline text, main-focus selection and unsupported controls require physical entry. An uncertain edit-message result is never retried as clipboard input. Background WM_CHAR delivery is explicitly unverified. Read-only/disabled controls refuse mutation.

The operation's last target is reused after foreground restoration. Fresh Win32 focus takes precedence over remembered native focus. Only an agent-established focus is remembered; subsequent click/focus/target changes invalidate it. Remembered controls must retain their HWND/PID/root and unchanged input-history stamp. An intervening user input with unavailable fresh focus returns `TARGET_FOCUS_CHANGED`; it does not guess the old field. Main focus explicitly chooses the largest enabled, keyboard-focusable, on-screen writable Edit/Document control. Optional native edit `verifyValue` is capped at 200 characters and excludes password edits. Physical entry does not read password values.

## Physical entry and cleanup

Explicit `sendinput` text uses KEYEVENTF_UNICODE down/up pairs for ordinary text, Enter key pairs for LF or CR (CRLF becomes one Enter), and Tab key pairs for tabs. Whitespace-only strings are valid text. These keys retain the target application's normal Enter/Tab behavior. A cancellable 50 ms gap follows each dispatched unit: both unpaced delivery and a 10 ms gap were observed to corrupt appended text in modern Notepad despite successful dispatch. The pinned DSH reference instead batches Unicode events without this per-character delay. Pacing and control-character handling changed together in Pi, so the successful regression does not establish that 50 ms is necessary or isolate the cause. See the [planned mechanism comparison](validation.md#unicode-mechanism-investigation). This provisional compatibility workaround adds approximately 50 ms per unit plus platform scheduling overhead; it is not a universal guarantee about application processing. Dispatch remains unverified until a subsequent observation confirms the intended text. Successful results expose `inputDelayMs` so callers can identify the pacing actually used by the running helper. Default `auto` entry retains its existing quiet-edit/clipboard routing. Chords are mapped using the target thread's keyboard layout and use SendInput rather than an uninterruptible SendKeys call. The shared activity observer spans the whole call and distinguishes our tagged key events from intervening physical/foreign injected input; a later synthetic key cannot erase earlier intervention evidence. The helper rechecks target HWND/PID, foreground and cancellation before each character/key; text also checks focused control and user-held modifiers/buttons. Every held key/modifier is released in `finally`, even when its key-down result was uncertain. Partial text, timeout and cancellation never authorize automatic replay.

The independent stop event and retained-input acknowledgment from [pointer stopping](pointer.md) cover keyboard actions too. A timeout signals the operation to stop; missing release/clipboard acknowledgment retains ownership and blocks worker termination/replacement. `set_value` may escalate only an explicit background `WCU_NEEDS_INPUT`, after re-resolving the observed control, checking enabled/read-only state and focusing it; select-all and typing use the same guarded cleanup.

## Clipboard transaction

Clipboard entry uses a separate STA process with a hidden message-only owner window and message pumping. All UIA focus work finishes before clipboard replacement; restoration never calls application rendering providers. The snapshot phase duplicates each available public clipboard format, including native bitmap/metafile formats, using [OleDuplicateData](https://learn.microsoft.com/en-us/windows/win32/api/ole2/nf-ole2-oleduplicatedata). When OLE transport markers (`DataObject` / `Ole Private Data`) are present, the helper validates the advertised FORMATETC descriptors before omitting those process-bound markers. Public formats must be unindexed content, without a target device, and available in supported native storage. All public native payloads are still duplicated. Unmaterializable, genuinely indexed, device-specific or unsupported OLE data fails before replacement rather than falling back to text-only preservation. Snapshot/rendering has a five-second process deadline while mutation is still forbidden.

Only a completed snapshot permits replacement. The helper publishes zero-valued history/cloud exclusion formats before Unicode text, following [Microsoft's clipboard format contract](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats#cloud-clipboard-and-clipboard-history-formats). Clipboard sequence checks protect an intervening user copy. Windows can also advance the sequence while synthesizing formats during paste; restoration across that change requires both the helper's hidden owner window and its unique transaction nonce. A different owner or missing nonce preserves the newer clipboard instead. Ctrl+V is followed by a cancellable bounded wait and native WM_NULL drain; a stalled target returns an uncertain-dispatch error. The original opaque snapshot is restored in `finally` before cleanup acknowledgment, or the explicit `restoreClipboard: false` result keeps the injected clipboard content. Cancellation/error always requests restoration. A newer user copy is preserved.

Cancellation, parent exit or a 30-second stalled transaction also triggers independent restoration. OpenClipboard acquisition has bounded retries. If another application indefinitely holds the clipboard or restoration fails, the helper retains duplicate originals, retries restoration and leaves cleanup/ownership unconfirmed. It is never force-killed after mutation or silently reported restored. This is a fail-closed recovery condition, not a guarantee that Windows will release another application's clipboard lock.

## Validation and pending acceptance

- `npm test`: normal worker validation for text options, malformed/ambiguous chords, Windows-key blocking and unsupported background chords, plus shared stop/non-replay lifecycle tests.
- `npm run test:native:text` after build: background Unicode/emoji, remembered target, WM_CHAR, read-only and wrong-target refusal on disposable forms. Native auto-edit checks use the backend's ordinary quiet-attempt protocol, so failure cannot escalate into physical input. This is backend-seam proof, not full Pi auto-escalation acceptance. The suite never reads or replaces the clipboard and sends no physical keys/mouse input.
- [Dedicated Windows runner instructions](validation.md#dedicated-physical-input-runners): Windows-only opt-in runner, **not run in this session**. It replaces clipboard content in a dedicated session, seeds Unicode/HTML/DIB/custom bytes, checks restoration after paste, exercises Unicode/chords, cancels ongoing text after fixture input and checks modifier release through the fixture. Read the runner before use and keep normal user applications off that desktop.

Physical paste, rich clipboard restoration, history/cloud behavior, synthetic Esc handling, real Esc stopping, password entry, focus interference and restoration after menus/dialogs remain dedicated/manual acceptance checks. The optional runner's presence and compiled helpers are not evidence those effects passed. Check unsupported delayed/indexed formats fail without mutation and a locked clipboard fails without input; verify user copying during entry wins over restoration and stopped text is not replayed until genuine new input. The shared [coverage plan](implementation-plan.md#coverage-matrix) remains authoritative for release evidence.

Dedicated restoration acceptance (unrun): during slow typing/main focus, move the pointer into the main field and select another pre-existing top-level window in the same process. Verify the pointer stays where moved and that window remains selected. Repeat with physical keyboard/mouse input followed by more agent-generated events, confirming earlier intervention still prevents restoration. Background pointer movement with unknown origin is left alone; field containment is never evidence that the agent moved it.

## Notepad Unicode regression

After building, run `npm run test:native:notepad:unicode` with Windows Node and `PI_CU_NOTEPAD_INPUT_TEST=1`. This opt-in test sends real input and temporarily activates Notepad; do not interact during it. It opens uniquely named empty temporary files, tests whitespace-only input, appending to a seeded document after Ctrl+End, the acceptance string, longer mixed Unicode, and LF/CR/CRLF/Tab handling. It compares both UIA values and independently saved UTF-8 bytes, normalizing only line endings. It saves and closes only its own test tabs, preserving test files/tabs for inspection if an action is uncertain. It never uses or changes the clipboard. Notepad installation and successful foreground activation are prerequisites; an activation refusal is a failure, not permission to bypass guards. This test does not establish emergency-stop, IME, password, clipboard or general activation acceptance.

## OLE clipboard regression

Preparation is portable and performs no clipboard or native actions:

```sh
npm run test:native:clipboard:plan
npm run test:native:clipboard:ole -- --plan --engine reference --reference /path/to/dsh-computer-use-win
```

The existing runner accepts `--engine pi` (default) or `--engine reference --reference <pinned-checkout>`. `--list-cases` and `--plan` report the same three prepared cases without importing a backend, creating fixture files or compiling/launching Windows helpers. Real execution requires Windows Node, a built Pi worker or pinned reference checkout, and `PI_CU_CLIPBOARD_INPUT_TEST=1` on a dedicated interactive desktop. **These paired physical runs are deferred; do not enable the opt-in on the ordinary user desktop.** The gate is checked before any clipboard access, fixture creation or backend import.

For a future explicitly enabled run, the fixture privately caches the original text/stream clipboard formats and restores only when it still owns the seeded clipboard; a genuinely intervening copy is preserved. Unsupported original fixture formats are refused before seeding. No clipboard payload is printed. The same fixture checks actual editor text independently against UIA, synthetic Unicode/HTML/binary preservation, indexed-OLE payload preservation with refusal before input, and synthetic newer-copy preservation. Raw tool results/errors and any optional cleanup diagnostics remain in the output; Pi-specific restoration labels/counts are not required from DSH. An explicitly unconfirmed cleanup blocks subsequent cases. Only owned fixture files/processes are eligible for cleanup; normal applications and documents are untouched.

The safe CLI checks establish preparation and gating only. Native compilation, actual paste, restoration and paired reference outcomes remain unrun in this stage. Plain-only clipboard, locked/delayed content, additional rich formats, history/cloud exclusion and remote desktop behavior still require additional dedicated acceptance; this runner does not claim that coverage.

Clipboard results expose `clipboardSnapshot` counts (`preservedFormats`, `oleMetadataExcluded`, `oleFormatsValidated`) and `clipboardRestoreOutcome`: `restored`, `newer-copy-preserved`, `kept`, or `unchanged` when no replacement was authorized. Cleanup confirmation alone is not a claim that the original clipboard was restored. OLE transport markers are regenerated by Windows/consumers as needed rather than restoring stale interface handles.
