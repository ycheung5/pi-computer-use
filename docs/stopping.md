# Emergency stopping

Use `/computer-stop` to stop the current computer-use operation without waiting for a tool response. Pi cancellation also stops the operation. Queued calls are cancelled, active work is signaled, and subsequent calls in that operation are rejected with `COMPUTER_USE_STOPPED`. A model turn, retry or custom continuation does not reset stopping; a genuine new user run does.

## Independent Windows listener

A small separate Windows process installs a low-level keyboard hook. It is armed by the internal `prepare_input` request and guarded native mutation paths, including background element scrolling; quiet reads and browser work do not arm it. Background element scrolling retains the cleanup lease while a synchronous provider call is outstanding, but never announces physical input to the presentation. Esc signals an operation-specific manual-reset Windows event directly, then notifies the worker. The listener never calls UI Automation and can signal while a native provider is blocked. Keyboard events continue to the target application; the hook does not swallow ordinary Esc behavior. It also supports the personal extra shortcut and ignores injected keyboard events, so agent Escape actions do not stop themselves. See [indicator lifetime and preview](indicators.md).

The explicit stop control bypasses the worker request queue. The worker blocks the operation before cleanup, signals its listener/event if armed, cancels active and queued requests and retires the read-only desktop bridge. Retirement waits for confirmed child exit; failure to confirm exit retains the child handle and sticky failure, blocks replacement work and is not permission to release ownership. Worker stdin closure also retains ownership if prior stop cleanup was unconfirmed. If a worker exits after reporting active input without a cleanup acknowledgement, its client rejects replacement work instead of starting a new worker; this fail-closed state requires external investigation. Final settlement waits for this stop cleanup before releasing desktop ownership. Cancellation is not an instruction to replay any action.

## Physical input contract

Pointer and keyboard actions use the cancellation event and report `inputReady: true` with an explicit `readyActions` list. See [pointer guards](pointer.md) and [text/clipboard cleanup](text.md) for pending physical acceptance. Each enabled action must:

1. Arm the independent listener before sending input and checks the operation's cancellation event.
2. Check cancellation between input steps and releases every held key/button in `finally`.
3. Confirm cleanup before retiring a native input bridge or releasing desktop ownership.
4. Handle listener failure and timeout without silently replaying input or claiming success.

Before physical dispatch, the worker now sends a private request-scoped preparation token and waits for the controlling client to acknowledge it. The client records the active-input lease before acknowledging; a missing or mismatched acknowledgement cannot start input. Stop or stdin closure while still waiting cancels preparation without dispatch. The worker clears the lease before dispatch only if preparation was cancelled; after dispatch, only the native cleanup acknowledgement clears it. This private worker/client protocol is not a public tool parameter. A raw older worker-protocol client that does not acknowledge `input_prepare` will stall before physical dispatch until it cancels or closes stdin; bundled clients use the updated acknowledgement. The real-worker protocol has deterministic coverage against disposable fake native processes; actual Windows input and crash behavior remain separate acceptance checks.

A blocked read-only UIA/capture process can be killed after a bounded grace period. Physical actions are implemented and advertised by `readyActions`; this is not proof that held keys/buttons are released correctly. Their dedicated interactive acceptance remains open.

## Validation

- `npm test` covers a busy disposable protocol peer, queued cancellation, same-operation rejection, custom-continuation rejection, Pi abort, new-user recovery and confirmed retirement of an unresponsive peer.
- After `npm run build`, `npm run test:stop` verifies real Windows hook registration, an initially unsignaled kernel event, signaling through the normal stop control, a distinct unsignaled event for the next operation, and worker rejection/recovery and a deliberately invalid pointer target refusal. It sends no keys or pointer input.
- The existing paired accessibility provider subset (`test:accessibility:report -- /path/to/reference --providers`) independently confirms the identified reader is alive after provider entry and absent after cancellation, before releasing its owned provider, followed by fresh-read recovery. This is native read-process cleanup, not held-input cleanup; see [provider evidence](validation.md#accessibility-comparison-evidence).
- A dedicated physical Esc run stopped busy typing in the Pi worker fixture and independently observed released keys; real Pi-host and DSH stopping, and held-key/button cleanup during physical actions, remain dedicated-desktop acceptance checks. Hook registration and explicit signaling are not reported as a physical-key test.

The [passive operation baseline](validation.md#passive-operation-evidence) records current results and reference source comparison. User-reported earlier Esc/command checks do not replace a recorded busy-input/held-key acceptance run. A rejected promise, hook registration or `cleanupConfirmed` alone cannot establish actual key/button release.

## Held-key acceptance boundary

Neither Pi nor DSH exposes a public key-down/hold/key-up operation; each `keypress` dispatches a complete chord. Observing a modifier up after cancellation does not establish that it was held when cancellation arrived. The legacy Pi-only long-typing fixture overwrote the original clipboard without restoring it and could retire an unsettled input owner; its runner now refuses execution before starting a backend. A paired long-typing cancellation case needs an independently observed input-settlement boundary before retiring its worker or fixture: Pi abort rejection can precede worker cleanup, and the DSH MCP adapter has no equivalent verified cleanup event. If cleanup cannot be confirmed, retain the owned processes/files and report uncertainty instead of killing a possible input owner or replaying input. Real Esc/custom shortcut behavior requires the actual host and a dedicated session; MCP cancellation alone is not that evidence. See [dedicated session evidence](validation.md#dedicated-physical-comparison-evidence).

### Clipboard-free manual worker fixture

After `npm run build`, run `npm run test:stop:busy -- esc` on a dedicated, unlocked Windows desktop with `PI_CU_DEDICATED_INPUT_DESKTOP=1`. The runner waits up to two minutes at a start gate: once the user is ready, send `start` followed by Enter to the runner's stdin. After it reports typing has started, physically press Esc once within 40 seconds. Use `shortcut` instead of `esc` in a separate fresh run to test the fixture's isolated `Ctrl+Alt+F9` setting. Both indicators are disabled in the fixture settings. Do not operate the desktop during the run except for the requested key. The fixture never reads or changes the clipboard.

When stdout is buffered, set `PI_CU_STOP_STATUS_FILE` to a new, nonexistent file in a private Windows-readable directory before starting the runner. Its JSON `phase` changes from `setup` to `ready`, then `started`; monitor it independently and relay the key prompt when it reports `started`. The caller sends the stdin start command only after the user is ready. The runner refuses to overwrite an existing status file.

The runner observes the disposable editor, the worker stop event, rejection of the stopped operation, acknowledged operation settlement, stable partial text, and released mouse buttons, modifiers, Esc and F9. After settlement it polls key state for up to five seconds to allow the user to release the physical shortcut; keys still held after that period fail the check. A pass also requires the input result itself to report `COMPUTER_USE_STOPPED` with confirmed cleanup; a generic worker cancellation or other input error is inconclusive. It checks a subsequent new worker operation. If input settlement cannot be confirmed, it retains the fixture, worker and temporary files rather than terminating a possible input owner; manual investigation is required. A timeout sends the normal stop control once and remains a failed physical-key test. These results cover the Pi worker and listener, not a real Pi session, DSH host, or cancellation while a modifier is known held. `npm run test:stop:busy:check` checks the outcome evaluator without desktop input.

### Passive registered-command fixture

After building, `npm run test:stop:pi-host -- command` selects the native-Windows no-input case; `--command-host wsl` selects a WSL2 Pi host with the same real Windows worker. Add `--plan` to either selector for a side-effect-free summary. The case uses installed Pi 1.4.0 and an isolated scripted provider. It uses the existing runner, real RPC host, production registered `/computer-stop` command and Windows worker; only health and wait tools are permitted. Hold the shared live-test lock for the entire run. No editor, window discovery, UIA, screenshot, clipboard or physical key is used. This mode does not relax the physical fixture's containment refusal below.

The finite sequence requests one 30-second wait, establishes an actual received/pending request plus independently observed ownership, submits `/computer-stop` through RPC, requires the actual matching worker wait response to report `COMPUTER_USE_STOPPED` before its original 30-second budget (same-process monotonic timestamps), gates later turns on its successful ownership-release acknowledgment, checks aborted settlement and same-operation custom-continuation refusal, then permits one fresh ordinary-user short wait under a distinct operation. A passive metadata-only Node preload observes existing worker protocol frames without introducing a worker/proxy owner or starting stdin flow early. It never rewrites or substitutes responses. Malformed/missing observer proof, deadlines or uncertain cleanup retain the actual host and keeper, deny further tools and authorize no kill, next reset or deletion. Reports stay in the printed owned temporary directory; successful cleanup removes only the isolated settings/agent directory.

Portable forwarding/callback, observer-fault and owner/tool guard controls run in `npm run check`; the existing keeper's fake-process retention checks remain binding. One independently reviewed native-Windows run on `73d4162` passed actual worker cancellation and release before continuation; [scoped evidence](validation.md#passive-operation-evidence) preserves that exact source. WSL-host adaptation still requires independent review and its own live run. Host identity and cleanup stay separate: Linux `/proc` start/executable identities never enter Windows PID queries, which start only from the Windows worker’s real returned PID. WSL-only relative settings, shared mapped cwd and child-only `WSLENV` forwarding keep settings/logs owned; worker metadata must confirm the actual cwd/override. This case cannot prove physical Esc/custom shortcuts, held-key/button release, DSH-host or real-model behavior.

### Scripted native Pi host fixture

`npm run test:stop:pi-host -- esc` is currently blocked before fixture startup or input: the real Pi host and its descendants do not yet have independently verified process containment. The separate process-containment prerequisite does not prove containment for this launcher. A generic `AbortError`, an `agent_settled` event and worker PID disappearance do not independently prove all native helpers exited. Do not bypass this guard. `npm run test:stop:pi-host:check` tests the outcome evaluator and blocked prerequisite without desktop input.

The passive job supervisor is not itself a safe physical-input supervisor: it kills job members if the supervisor dies. The no-input [crash boundary fixture](text.md#isolated-clipboard-diagnostics) separately demonstrates that the killed synthetic worker's managed `finally` does not execute, although the normal control's does. Pi's input paths release held inputs in `finally`; the synthetic result is a reason to retain the physical gate, not an observation of an actual held key or button.

The separate `npm run test:stop:pi-host:job` prerequisite requires Windows Node, a built package and `PI_CU_PI_CLI` pointing to the installed Pi CLI. A test-only supervisor starts suspended, enters a Windows job and launches the native Pi CLI with an isolated scripted provider. It sends no physical input, exercises health, list-windows and a wait, observes the distinct Pi host, worker and a process named `windows` in the job, then requires the job to be empty. The process name alone does not establish its executable path or parentage. Its temporary stdout may contain a window title and is removed on completion. Its synthetic provider and passive launcher do not establish containment of the physical stop launcher or independently exclude escaped/external descendants. `npm run test:stop:pi-host:job:check` checks the evidence evaluator without Windows.

After the containment gap is resolved, this planned fixture uses the dedicated desktop opt-in and stdin/status-file coordination above, plus `PI_CU_PI_CLI` pointing to the installed native Windows Pi CLI. It starts the real Pi RPC host with an isolated scripted provider and settings, not a real model or the user's Pi profile. `shortcut` selects the separately configured physical key. Its intended checks include the target editor observing the requested key while the tool is active, an aborted `agent_settled` event without extension errors, stable partial text, released keys and confirmed Pi/worker exit. A time limit requests Pi's normal abort; uncertain settlement or shutdown retains the host and fixture rather than killing a possible input owner. The path is scoped to the native Windows Pi host and would not establish WSL-host, DSH, real-model or held-modifier behavior. Live acceptance remains pending.
