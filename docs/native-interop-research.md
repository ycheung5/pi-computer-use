# Native interop comparison — research notes

Scope: Windows-side worker launched by native Pi or WSL2; the choice should not require users to install another extension. This is a source/documentation comparison, not a prototype, benchmark, exhaustive package survey, or proof of the globally smallest implementation.

## Established facts

- Current source uses a persistent out-of-process C# bridge, built lazily using the Windows .NET Framework64 compiler, with TypeScript managing lifecycle; UIA runs on an MTA thread. The project's `docs/windows.md` records a Windows 11 x64 WSL run and notes missing compiler failures and untested configurations. `docs/runtime.md` records separate Windows Node provisioning and its tested bounds. This is an actual selected design and scoped feasibility evidence, not evidence it outperforms every alternative.
- Node-API is a stable ABI for native addons, which are native code modules loaded by Node ([Node-API](https://nodejs.org/api/n-api.html), [Node addons](https://nodejs.org/api/addons.html)). Calling the C++ Windows interfaces through an addon can present a TypeScript interface, but requires implementing or adopting and distributing native code. Node advises moving long-running addon work off the event loop. A worker thread avoids blocking the event loop but does not itself isolate native process crashes; a separate process can provide that boundary (engineering inference).
- Koffi is a concrete Node FFI option: its maintainers document C calls, structs, pointers and callbacks, Node 16+, and packaged prebuilt Windows x64/arm64 binaries ([overview](https://koffi.dev/)). Callback declarations, registered lifetime, threading and calling conventions need care ([callbacks](https://koffi.dev/callbacks)). This adds a native runtime dependency despite TypeScript-facing declarations. Those capabilities do not demonstrate complete UIA/WinRT bindings or behavioral parity for this application.
- The current pinned Windows runtime is Node 22.23.4 (`docs/runtime.md`). Node's built-in `node:ffi` was added in 26.1 and is experimental, unsafe, and restricted by callback thread and lifetime rules; it is not an option in the pinned runtime without changing that runtime ([Node FFI](https://nodejs.org/api/ffi.html)). Neither a Node version upgrade nor experimental FFI is established as necessary here.
- UIA is COM-based; Microsoft recommends a separate MTA thread for a client interacting with all desktop elements and notes that COM element lifetimes can depend on their originating apartment ([UIA threading](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading)). An FFI/addon implementation must solve the same COM object, apartment and cleanup problems; generic C-call support alone does not establish that those problems are solved.
- Capture in this project includes HWND interop and a free-threaded Direct3D frame pool, not only a raw desktop bitmap ([CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), [CreateFreeThreaded](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded)). OCR uses the Windows Runtime OCR API's asynchronous operation and bitmap ([RecognizeAsync](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine.recognizeasync?view=winrt-20348)). Microsoft’s [OCR namespace documentation](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr?view=winrt-26100) states desktop support requires package identity; the project's observed fixture success on its tested host does not resolve that documented support limitation for unpackaged installations. Do not claim broad supported clean-install OCR from that success.
- Physical input uses Windows `SendInput`, which accepts native structures and is subject to UIPI ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). A low-level keyboard hook requires a message loop on its installing thread and must return promptly; Windows may silently remove a timed-out hook ([LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)). These Windows restrictions do not disappear through FFI or an addon.

## Engineering judgment and unresolved tradeoffs

Retain the current helper provisionally: it already supplies the required apartment, OS bindings, and process boundary without another Pi extension or additional Node FFI dependency, with recorded scoped validation. This supports a practical maintainability decision relative to the two identified approaches; it does not prove minimum size or that Koffi/Node-API could not improve selected functions. The helper still depends on the Windows Framework compiler, WinRT availability and platform-specific code, incurs compilation/process costs, and needs explicit handling of blocked or failed providers. A native addon/FFI approach could simplify isolated Win32 calls or packaging in some scenarios, but would require new bindings, architecture/distribution evaluation and the same semantics, isolation, stop and cleanup evidence; no fair implementation comparison or performance measurements have been made. Revisit when a concrete improvement demonstrably preserves those behaviors on native Windows and WSL2, including clean installation, supported architectures and failure paths. No current evidence warrants a rewrite.
