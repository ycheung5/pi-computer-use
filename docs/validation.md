## Reproduce automated checks

From a clean checkout with Node 22.19+ and npm:

```sh
npm ci --ignore-scripts
npm run check
npm run build
npm run test:package
npm run test:parity -- /path/to/dsh-computer-use-win
```

`test:package` packs/extracts the actual distribution and verifies its required assets plus every local Markdown link/heading. `test:parity` reads the reference's advertised schemas without desktop calls, comparing all 25 declarations and supported parameter types, defaults, enums, required fields, array/numeric/string bounds, patterns and additional-property restrictions. It does not compare prose or prove runtime behavior. Extra native signed-32-bit bounds on move_window X/Y are reported explicitly. The inspected reference baseline is 0.5.3 at commit `6fb642129595a6357588c70812974951db304662`.

On WSL2, serialize all live checks:

```sh
flock -w 120 /tmp/pi-cu-live-tests.lock npm run test:pi
```

`test:pi` creates a new tarball and installs it in a disposable consumer directory with development and peer packages omitted. It loads the result through the real Pi CLI using Pi's public offline faux provider. Normal agent turns execute only health/list_windows, reach settlement and shut down the worker; no paid model, physical input, clipboard mutation, normal browser profile or daily Pi settings are used. On WSL2 it also launches a native Windows Pi CLI with the private runtime. On Windows it exercises that host alone. It verifies host-provided packages resolve without being bundled in the consumer package. `PI_CU_RELEASE_OUTPUT` can name a directory for sanitized JSON evidence; raw desktop window titles are not retained.

This runner uses the installed development Pi 1.4.0 distribution as the test host, not a fresh OS/Windows Pi install. Its scripted provider is a test fixture, never a production dependency. Real provider quality, interactive terminal workflows, and dedicated input/user acceptance remain separate checks.

The separate `test:pi:browser` companion reproduces the three scoped real-model outcomes (`form`, `advanced`, `stale`) using the existing local server and isolated headless Edge profiles. It uses the installed Pi host and its existing authentication; no credentials are printed or bundled. Unlike `test:pi`, it makes paid model requests. First build and follow [Windows-readable dependency prerequisites](runtime.md#verification). Preview safely without a build, Windows launch, credential lookup or file write:

```sh
npm run test:pi:browser -- --plan
```

Select a named case or `all` and one to three independent resets; the defaults are OpenAI, GPT-6.1 Sol and low reasoning. Requested settings and actual assistant metadata are recorded separately. For example:

```sh
PI_CU_RELEASE_OUTPUT=/tmp/pi-browser-evidence flock -w 120 /tmp/pi-cu-live-tests.lock npm run test:pi:browser -- --scenario stale --runs 3 --provider openai --model gpt-6.1-sol --thinking low
```

The test-only `PI_CU_TEST_TIMEOUT_MS` sets a 50–180000 ms episode watchdog (default 180000); expiry retains ownership rather than terminating it. Each unique output directory contains its tool trace, independent report and `owner.json`. A normal report requires actual observations, exact server/file oracles, Pi settlement and scoped cleanup. Stale refreshes are explicit fixture-controlled public-tool navigation; the product must return the real stale refusal and the agent must recover with its own new observations. Prior private three-run results below remain historical evidence, not validation of this new collector. A retained report is a failure requiring investigation: its referenced keeper preserves uncertain ownership and fixture pipes, blocks later actions/cases and records identities in `owner.json`; do not treat it as completed cleanup or wait indefinitely for a pass. There are no automatic retries or arbitrary browser termination.
