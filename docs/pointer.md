# Guarded pointer actions

`click`, `double_click`, `move`, `drag` and coordinate `scroll` use screen coordinates in physical desktop pixels. Convert image coordinates using the screenshot's `origin`, `imageScale` and `imageScaleY`; do not treat a resized PNG's pixels as desktop coordinates. Negative monitor coordinates are supported. Observed HWND/PID origins are scoped to the operation; source-window movement shifts coordinate points/the whole drag path by the observed delta. A remembered title resolving to a replacement window fails closed until fresh observation.

Auto left clicks on an observed element try native/UIA background behavior, then unconfirmed background messages. Explicit `dispatch: background` posts messages and never authorizes physical fallback. Auto double/right clicks and `dispatch: foreground` use physical input. Move retains the requested hover position and activates only with `activate: true`. Other physical actions return the pointer when it is still where automation left it; foreground restoration respects `activate: true`, user movement/focus changes and opened menus/dialogs. Target activation shares the existing native thread-attachment helper used by window management, without synthetic Alt/keyboard workarounds. Windows may refuse foreground activation/restoration; results report that refusal.

Before physical input, the worker arms the independent Esc listener and passes its operation-specific cancellation event and retained process identity to the native helper. The helper checks target HWND/PID, enabled/visible state, foreground, source identity and source-or-visible-same-process-popup hit testing immediately before dispatch. A covering window from the same process also fails the check. Held user buttons/modifiers refuse takeover. Drag validates screen bounds and the starting point against the source or its visible same-process menu/dialog, including popups outside the source frame and enabled modal dialogs whose source frame is disabled. It permits cross-window drops and destination foreground activation, keeps checking source identity, cancellation and pointer/user interference between steps, and releases its button in `finally` before any restoration/provider work. There is no automatic replay after uncertain dispatch, timeout or cancellation. Only a background `WCU_NEEDS_INPUT` result, generated before input, permits guarded invoke/element-scroll fallback.

A missing cleanup acknowledgment retains desktop ownership and blocks replacement work. Both bridge and outer-worker clients refuse force termination while input may be active; the flag clears only after the native button-up cleanup acknowledgment. A release failure remains closed rather than allowing another operation to send input. [Keyboard and clipboard actions](text.md) share this cleanup contract.

Successful input/background operations remember the exact target HWND/PID for this operation. Later targetless observations and input use that identity after foreground is returned. Explicit targets, browser requests, element references and explicit desktop scope take precedence. Settlement clears the remembered target; a stale identity fails rather than guessing the user's current foreground. Screenshots retain their existing full-desktop versus window-capture semantics.

## Validation

- `npm test`: worker argument validation and the public worker lifecycle contract that prevents retirement while cleanup is unconfirmed. These portable tests do not prove Windows input delivery.
- `npm run build` then `npm run test:native:pointer:guards`: dedicated passive fixture, background click/double click, last-target observation, stale/wrong-owner refusal, outside points and covered-point refusal. Sends no physical input. Uses the same Windows runtime setup as [runtime validation](runtime.md).
- `npm run test:native:controls`: background controls regression; unsupported invoke fallback is explicitly disabled so this suite stays free of physical input.
- `npm run test:native:pointer:physical -- --list --engine=reference`: safe WSL plan only; does not load a backend, inspect files, compile a fixture or contact Windows. Execution without `PI_CU_DEDICATED_INPUT_DESKTOP=1` refuses before those operations. Unknown options/engines fail rather than silently selecting a backend.
- [Dedicated Windows runner instructions](validation.md#dedicated-physical-input-runners): the existing runner now selects `--engine=pi` (default, registered Pi tool execution) or `--engine=reference --reference=<Windows-readable-reference-path>` (public MCP). Each invocation creates a fresh controls fixture and stops on failure; there is no input replay or method switch. It prepares scaled-point click, exact double-click count, actual hover, inner-panel scroll and drag-cancellation release checks. Fixture-owned counters/hover/scroll state and the OS left-button state supply independent outcomes; raw action/errors are retained as diagnostics without requiring Pi-specific method/restoration fields. The later [dedicated physical baseline](validation.md#dedicated-physical-comparison-evidence) records executed cases and retained failures.

Before release, run the physical runner at 100%, 150% and 200% display scaling and on a monitor with negative origin. Manually stop a drag with real Esc and `/computer-stop`, verify no replay until new user input, and inspect restoration after user pointer/focus interference and menu/dialog opening. Test target disappearance/replacement between observation and input. These physical and manual acceptance checks remain pending; hook installation, simulated protocol cleanup notices and no-input refusals are not substitutes for them. Cross-application drag/drop effects also remain a dedicated physical acceptance check.

## Corrective acceptance cases

The passive `test:native:pointer:guards` fixture reproduces the old outside-frame popup refusal and verifies corrected background dispatch to an owned popup, while stale/wrong-PID, foreign/ordinary-window coverage and no-input refusals remain enforced. Shared hit testing admits the source or a visible same-process owned/popup window, never an arbitrary other process or our indicator overlay.

On a **dedicated interactive desktop**, use the opt-in physical runner/fixture for these additional pending cases: open a menu/dialog outside the source frame and physically select its item using the source target; drag across a second application whose destination activates during hover and verify the drop completes; then repeat while physically moving the pointer or pressing a key mid-drag and verify button release without replay. Move the pointer away and back to the agent's last coordinate while a call is active: the activity observer must still prevent restoration. These cases are unrun here. When key/button cleanup is unconfirmed, restoration itself stays disabled so it cannot drag or direct a held modifier into the user's prior window.

## Drag failure reporting

The physical runner now waits for the drag and fixture mouse-down observation to settle, then records bounded read-only release observations **before** asserting the dispatch outcome or tearing down the fixture. A timeout, unexpected success/error or missing fixture reply retains its original evidence together with button-held state, release-counter progression and any observation error. The report distinguishes cancellation confirmation from release confirmation; a released button does not turn a timeout into successful cancellation. No automatic button release, new input or replay is performed by this reporting step. A held or unconfirmed state requires the coordinator to stop dependent physical tests and arrange separately verified cleanup.

An offline saved-evidence check is available through the existing runner CLI:

```sh
npm run test:native:pointer:physical -- --report-drag=/path/to/drag-evidence.json
```

It runs before Windows/desktop opt-in and starts no client, fixture or input. Save the emitted report's `evidence` object as the input. Portable regressions distinguish cancelled-and-released, timed-out-and-held, timed-out-but-released, absent mouse-down and unavailable release observation. These reporting checks do not rerun or repair DSH's recorded physical cancellation failure. Live use of the updated error path remains pending the next dedicated session.

The separately selected `--case=drag-drop` prepares a fresh owned Windows Forms drag source and drop target for each engine. The target counts an actual OLE drop carrying the fixture payload, independently of the engine's result; the fixture also reads the OS left-button state. A pass requires a successful dispatch, exactly one observed drop and a released button. For example, first inspect the plan with `npm run test:native:pointer:physical -- --list --engine=reference --case=drag-drop`; run each engine only under the dedicated Windows prerequisites above. The case never retries input. A failed or timed-out dispatch, an unreadable oracle, or a held button retains the engine and fixture instead of terminating a potentially active input owner; stop dependent tests and investigate. This fixture tests a same-application drop; cross-application and user-interference tests remain pending. Fresh Pi and DSH runs each recorded one drop and an independently observed released button; see [validation evidence](validation.md#successful-dragdrop-fixture-preflight).

The first Pi drop run stopped before input because neither fixture panel appeared in UIA, including raw-view observations after a delay. The fixture now uses standard button controls with the same drag/drop handlers. `--case=drop-discovery` is a Windows-only passive preflight: it creates a fresh owned fixture, records control and raw trees, and reports UIA discovery separately and checks fixture-owned source/target geometry against the independently observed window identity and bounds. It sends no pointer or keyboard input but creates a normal window that can activate, so the dedicated desktop opt-in remains required. The physical case uses freshly observed geometry and stops before input if its checks fail. Subsequent no-input preflights found both controls on each engine, followed by successful paired physical drops as recorded in the validation evidence.

The original fixture used a hidden Windows process launch. Separate passive probes found an OS-hidden fixture and observed source and target buttons after launching the fixture visibly. The runner now starts a visible fixture and requires OS window visibility and a root observation that is not offscreen before input; this still requires dedicated live preflight and does not establish a successful drop.

## Native-menu comparison preparation

`test:reference:focus-foreground -- --plan --native-menu --provenance` lists a separate Win32 `TrackPopupMenu` fixture. On an explicitly authorized idle Windows desktop the same options, plus engine selection, invoke its owned button without physical input. A result requires a visible native menu window, its target GUI thread's menu-owner and menu-mode evidence, a matching menu item from the engine UIA find, and repeated foreground/menu observations. The UIA item lookup is not an independent client. Reads are successive, not atomic. Missing or ambiguous identity, unobserved UIA item or unavailable menu mode remain inconclusive; an unresolved action retains its owned processes. Before normal cleanup, the fixture must confirm a posted dismissal, a queued acknowledgement after the modal menu handler returned, and native menu mode/window closure; otherwise it retains the backend and fixture. The fixture is compiled and its offline planning/report checks run, but no live native-menu run has been performed; it does not establish cross-application menu or user-interference behavior.
