# Guarded pointer actions

`click`, `double_click`, `move`, `drag` and coordinate `scroll` use screen coordinates in physical desktop pixels. Convert image coordinates using the screenshot's `origin`, `imageScale` and `imageScaleY`; do not treat a resized PNG's pixels as desktop coordinates. Negative monitor coordinates are supported. Observed HWND/PID origins are scoped to the operation; source-window movement shifts coordinate points/the whole drag path by the observed delta. A remembered title resolving to a replacement window fails closed until fresh observation.

Auto left clicks on an observed element try native/UIA background behavior, then unconfirmed background messages. Explicit `dispatch: background` posts messages and never authorizes physical fallback. Auto double/right clicks and `dispatch: foreground` use physical input. Move retains the requested hover position and activates only with `activate: true`. Other physical actions return the pointer when it is still where automation left it; foreground restoration respects `activate: true`, user movement/focus changes and opened menus/dialogs. Windows may refuse foreground activation/restoration; results report that refusal.

Before physical input, the worker arms the independent Esc listener and passes its operation-specific cancellation event and retained process identity to the native helper. The helper checks target HWND/PID, enabled/visible state, foreground, source identity and source-or-visible-same-process-popup hit testing immediately before dispatch. A covering window from the same process also fails the check. Held user buttons/modifiers refuse takeover. Drag validates screen bounds and the starting point against the source or its visible same-process menu/dialog, including popups outside the source frame and enabled modal dialogs whose source frame is disabled. It permits cross-window drops and destination foreground activation, keeps checking source identity, cancellation and pointer/user interference between steps, and releases its button in `finally` before any restoration/provider work. There is no automatic replay after uncertain dispatch, timeout or cancellation. Only a background `WCU_NEEDS_INPUT` result, generated before input, permits guarded invoke/element-scroll fallback.

A missing cleanup acknowledgment retains desktop ownership and blocks replacement work. Both bridge and outer-worker clients refuse force termination while input may be active; the flag clears only after the native button-up cleanup acknowledgment. A release failure remains closed rather than allowing another operation to send input. [Keyboard and clipboard actions](text.md) share this cleanup contract.

Successful input/background operations remember the exact target HWND/PID for this operation. Later targetless observations and input use that identity after foreground is returned. Explicit targets, browser requests, element references and explicit desktop scope take precedence. Settlement clears the remembered target; a stale identity fails rather than guessing the user's current foreground. Screenshots retain their existing full-desktop versus window-capture semantics.

## Validation

- `npm test`: worker argument validation and the public worker lifecycle contract that prevents retirement while cleanup is unconfirmed. These portable tests do not prove Windows input delivery.
- `npm run build` then `npm run test:native:pointer:guards`: dedicated passive fixture, background click/double click, last-target observation, stale/wrong-owner refusal, outside points and covered-point refusal. Sends no physical input. Uses the same Windows runtime setup as [runtime validation](runtime.md).
- `npm run test:native:controls`: background controls regression; unsupported invoke fallback is explicitly disabled so this suite stays free of physical input.
- `PI_CU_DEDICATED_INPUT_DESKTOP=1 npm run test:native:pointer:physical`: opt-in Windows-only runner. It emits physical input to its disposable fixture and cancels a drag after the fixture receives button-down. Run only on a dedicated interactive desktop. It verifies the scaled screenshot-to-screen point, click/double click, hover, coordinate scrolling and button release after Pi cancellation. It has **not been run in the user's normal desktop session**.

Before release, run the physical runner at 100%, 150% and 200% display scaling and on a monitor with negative origin. Manually stop a drag with real Esc and `/computer-stop`, verify no replay until new user input, and inspect restoration after user pointer/focus interference and menu/dialog opening. Test target disappearance/replacement between observation and input. These physical and manual acceptance checks remain pending; hook installation, simulated protocol cleanup notices and no-input refusals are not substitutes for them. Cross-application drag/drop effects also remain a dedicated physical acceptance check.

## Corrective acceptance cases

The passive `test:native:pointer:guards` fixture reproduces the old outside-frame popup refusal and verifies corrected background dispatch to an owned popup, while stale/wrong-PID, foreign/ordinary-window coverage and no-input refusals remain enforced. Shared hit testing admits the source or a visible same-process owned/popup window, never an arbitrary other process or our indicator overlay.

On a **dedicated interactive desktop**, use the opt-in physical runner/fixture for these additional pending cases: open a menu/dialog outside the source frame and physically select its item using the source target; drag across a second application whose destination activates during hover and verify the drop completes; then repeat while physically moving the pointer or pressing a key mid-drag and verify button release without replay. Move the pointer away and back to the agent's last coordinate while a call is active: the activity observer must still prevent restoration. These cases are unrun here. When key/button cleanup is unconfirmed, restoration itself stays disabled so it cannot drag or direct a held modifier into the user's prior window.
