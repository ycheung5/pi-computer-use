# Browser read channel

Pi's normal tools route to the Windows browser worker when given `browserTab` or a browser element ID. `set_value` with `elementId: new-tab` opens a URL in a dedicated browser context; `<tab>:address` navigates it. `list_windows` annotates connected browser/tab IDs. Snapshot, accessibility_tree, find, element_info and screenshot work in this channel. Snapshot emits its PNG as an image block, with base64 omitted from text metadata.

Browser `element_info` includes disabled and read-only state for applicable controls, including native disabled state and disabled/inert DOM-ancestor and element-local ARIA states. Ancestor checks do not cross shadow roots, and inherited ARIA read-only state from a containing grid is not inferred. Read these observations before choosing an action; they do not grant permission to bypass a restricted control.

Installed Chrome and Edge are discovered from Windows default-browser registration, App Paths and conventional locations. The worker uses pinned puppeteer-core 25.16.0 with explicit installed executables, CDP, no managed browser downloads and no daily profiles. Temporary profiles and an isolated browser context are created by the worker. Background target creation is explicit. The Chromium channel supports reading/navigation and guarded element interactions, page text/key input, scrolling, explicit waits, JavaScript dialogs, popups, upload/download metadata and tab closure. Experimental installed Firefox uses a separate WebDriver BiDi channel described below. Dedicated kept profiles are opt-in as described below. Browser drag remains unsupported as in the reference.

Browser `type_text` and common editing keypresses refuse a focused element with explicit `aria-readonly="true"` or a focused element in a disabled/inert context. Directional keys are also refused for native value controls such as number, range, date and select, and equivalent explicit ARIA roles; text-field navigation, selection and dialog keys remain available. The typing and keyboard guards inspect the focused element through open shadow roots and same-origin iframes, accumulating disabled/inert state from the host or frame at each boundary. Closed shadow roots and cross-origin frames remain opaque: existing keypress behavior is retained, and `type_text` still refuses an opaque focused frame. The guard does not infer inherited ARIA grid state, custom widget behavior, or prevent arbitrary page scripts reacting to keys. HTML `readonly` blocks `set_value` only for input types and textareas where the attribute applies. An ignored attribute on a checkbox or radio does not make it read-only; explicit `aria-readonly` is still respected.

## Identity and coordinates

Tab IDs are salted per launch; element IDs are scoped to one tab document. Navigation clears observed element handles; disconnection withdraws tabs. Re-observe after navigation/reconnect rather than reusing old IDs. Never mix native HWND/PID/title or desktop x/y with browser references. Browser image bounds use page pixels and carry their actual width, height and imageScale; they are not desktop screen coordinates.

Browser focus checks the active element in the target's document or shadow root. An open-shadow editor can therefore report successful focus when the page document itself reports its host as active. A headless Edge fixture exercises focus and text entry through Pi tools; this does not establish focus behavior for closed shadow roots or cross-origin frames.

## Configuration and limits

Use `/computer-settings` to select browserApp and browserVisible in personal settings. Default is a visible browser following the Windows Chrome/Edge default, with installed-browser fallback. `PI_CU_BROWSER_EXECUTABLE` is an optional local executable-path override, not a model tool parameter. Fixtures use isolated settings files and never modify personal settings.

The Chromium outline comes from the accessibility tree. Traversal returns explicit truncation at budgets, but fetching an underlying AX tree or native browser protocol command can outlast the traversal budget; worker deadlines remain the outer safeguard. Page text is untrusted. An outline/page change proves neither user intent nor objective success. Browsers may activate for native dialogs; interaction behavior is validated in its own slice.

Own browser processes close gracefully on worker disposal or idle retirement. Temporary profile directories are removed only after their browser process is confirmed dead; kept profiles survive. Unknown or live orphan ownership is retained and reported rather than stolen.

Source: [Puppeteer installation](https://pptr.dev/guides/installation), [background page options](https://pptr.dev/api/puppeteer.createpageoptions), [accessibility snapshots](https://pptr.dev/api/puppeteer.accessibility.snapshot). Puppeteer is Apache-2.0 licensed; the package includes its license notice.

## Chromium interactions

Use observed browser element IDs for click, double-click, hover, focus, invoke and field values; browserTab selects the page for typing, keypress, scrolling and waits. Inputs stay inside the browser protocol. Target/disabled/readonly/occlusion checks run in a separate browser world so page code cannot simply replace the guard's DOM methods. The Windows worker serializes calls, retains operation ownership and honors stop/cancellation before subsequent inputs.

Ordinary browser actions return a bounded fresh outline/page-change report with `verification: sent`; this is evidence to inspect, not proof of the user's objective. Explicit waits return observed, timeout or inconclusive when budgets prevent proving absence. A post-action observation failure is recorded separately without replaying the action. Pending navigation is reported as still loading rather than navigated successfully.

An open JavaScript dialog blocks other page reads/actions. `keypress` Enter accepts it and Escape dismisses it; `type_text` supplies a prompt answer before Enter. Browser-window shortcuts such as Ctrl+L/T are refused; use address/new-tab tools. Background operation is the default; explicit activate_window is allowed to activate. Native JavaScript dialogs may affect foreground in visible browsers, matching the reference limitation.

File inputs take existing absolute Windows file paths, one per line or separated by `|`. An intercepted chooser reports an observed input ID instead of opening the OS file dialog. Chromium downloads report their state/name/file metadata under the package's Windows downloads directory; action-triggered popups return new tab IDs. None of these operations uses the user's daily browser profile.

Run `npm run test:browser:actions -- edge` or `-- chrome` after building. The default action fixture is headless; append `--visible` for the visible-browser check. It exercises text/chords, occlusion (including a page override of elementFromPoint), disabled/readonly controls, select/checkbox, dialogs, scroll/waits, transfers, popup/close and operation cancellation recovery through the Pi tool/worker interfaces. Live suites are serialized externally with the shared lab lock when multiple development agents use the same desktop.

Action validation uses the executable/version/headless assertions above; see corrected evidence and Firefox proof below. Physical keyboard/mouse input was not used.

## Experimental installed Firefox

Select `browserApp: firefox`; automatic Firefox-family launches are always headless, and settings normalize browserVisible to false. An OS Firefox default alone does not enable this experimental channel. Discovery checks the Firefox default ProgID command first, then registered App Paths and conventional Firefox locations. Both application.ini and browser/application.ini are accepted only with Firefox's App.ID in the App section; names alone do not establish engine compatibility. `PI_CU_BROWSER_EXECUTABLE` can select an unmodified Firefox-family executable explicitly. No managed or patched Firefox is downloaded by the extension.

The Firefox outline is explicitly `browser-dom-heuristic`, not a native accessibility tree. Roles and names are approximations from DOM controls, labels and ARIA. Elements remain document-scoped, with isolated-realm guards, ownership, stop/cancellation, dialogs, waits and post-action outlines shared with Chromium. The adapter's narrow isolated-realm seam uses a pinned Puppeteer internal interface because the public BiDi API does not expose accessibility or an isolated guard world; upgrades require live guard validation.

Reference limitations remain explicit: iframe contents, closed shadow roots, canvas semantics, file upload/download, browser drag and visible Firefox focus/sign-in flows are unsupported. Firefox screenshots capture the viewport and explicitly report that maxWidth is ignored. Forks and ESR versions require their own validation. Automatic crash replay is never attempted; a caller can explicitly create a new tab after a disconnected session has been withdrawn.

`PI_CU_BROWSER_BIDI_URL` explicitly connects to a loopback `ws:` endpoint with no credentials or fragment (root path becomes /session). It discovers existing tabs and uses the endpoint's existing default context, including its cookies. Disposal disconnects without closing the external browser or its existing/new tabs. Do not configure daily-profile endpoints. Run `npm run test:browser:firefox:endpoint` from Windows Node with PI_CU_BROWSER_EXECUTABLE to validate external process preservation in an owned fixture. Pass an optional reference checkout path to compare the same explicitly owned endpoint through reference MCP. This checks existing/new tabs, synthetic-cookie sharing, process preservation on disconnect and absence of an owned profile; real sign-in and daily profiles are excluded. An optional reference-checkout argument additionally checks the same explicitly owned endpoint through reference MCP, including pre-existing/new tabs, shared synthetic cookies, no owned profile creation and process preservation after disconnect.

Proof in this workspace used an official unmodified Mozilla Firefox 144.0 Windows binary extracted into a disposable fixture directory, without running its installer or changing browser registration. WSL2 Pi tool tests passed DOM outline/find/inspection, viewport screenshots, stale IDs, explicit reconnect, CJK/emoji/multiline values, password-value redaction, guarded actions, text/chords, scroll/waits, all three JavaScript dialogs, popup/close, transfer refusal and operation cancellation/recovery. The full action suite also passed from a native Windows Pi host. A native Windows endpoint fixture rejected a non-loopback URL and preserved its externally owned process on valid disconnect. No Firefox forks/ESR or visible/sign-in workflows are claimed validated. No physical desktop input was used.

For installed Firefox run `npm run test:browser -- firefox --headless` and `npm run test:browser:actions -- firefox`. An optional explicit executable is forwarded by WSL fixtures; each fixture asserts the actual launched executable/version/headless flags. Serialize live suites with the shared lab lock when multiple agents use the desktop.

## Dedicated profiles and idle retirement

`browserSignIn: false` remains the default: each launch uses a new temporary profile and an isolated browser context. With `browserSignIn: true`, the worker uses the dedicated profile's default context so cookies can persist, rather than an incognito context that would discard them. Kept storage is partitioned by browser and normalized executable path, so Edge, Chrome and Firefox installations do not share sign-ins. This never opens a daily profile. Normal graceful shutdown and idle retirement close the browser to flush cookie storage; abrupt termination cannot promise a final flush.

Storage defaults to `%LOCALAPPDATA%\pi-computer-use\browser`. `list_windows` reports the active automation profile's path and kept status. `PI_CU_BROWSER_PROFILE_ROOT` optionally chooses another storage root; the extension still creates its own kept/temporary subdirectories, never uses the root as a daily profile. To forget a dedicated sign-in, close its Pi workers and automation browser processes, then remove that reported kept directory and its adjacent `.lock` directory. Closing tabs or turning browserSignIn off does not erase stored sign-ins. Never remove a lock while an owner may still be live.

Each launch claims an atomic profile lease containing the worker PID, launch phase, browser PID and random ownership token. A second controller refuses a live owner. A dead worker with a live browser remains blocked. Recorded temporary profiles abandoned by confirmed dead workers/browsers are swept during the next profile acquisition. Kept-profile lock recovery requires both recorded processes to be dead; PID reuse conservatively blocks recovery. Missing, invalid or incomplete launch ownership is also blocked for manual inspection, since an unknown child must not be treated as dead. Cleanup never kills a PID obtained from an old lease. An unconfirmed launch/cleanup reports retained storage instead of deleting potentially live data.

Browsers retire after ten minutes without a completed browser call. Active actions and waits protect the browser until their full promises settle; listing/health calls do not indefinitely keep it open. `PI_CU_BROWSER_IDLE_MS` can change the timeout from 1,000 to 86,400,000 milliseconds (default 600,000), useful for shorter-lived shared-desktop sessions or longer interactive workflows. Retirement withdraws old IDs; an explicit new-tab request creates a new identity and reloads a kept profile. External loopback endpoints get no owned profile: their existing/default context and discovered tabs remain externally owned; retirement/disposal disconnects and preserves the process and all existing/new tabs.

Run `npm run test:browser:profiles -- edge`, `-- chrome`, or `-- firefox` after building; append `--temporary-crash` to check cleanup of recorded dead temporary profiles; use an installed Firefox executable override where needed. The Windows-local fixture uses an HTTP-only persistent synthetic cookie, disposable settings and its own storage root. It distinguishes cookie persistence from real sign-in support, checks temporary isolation/removal, live contention, idle retirement and active-wait protection, and observes whether a deliberately crashed worker leaves a live browser or Windows closes its child process. Surviving live orphans must be refused; confirmed dead owners can recover.

Manual release check: on a dedicated automation profile with browserSignIn enabled, complete a real site's sign-in yourself, shut down Pi normally, restart, and verify the intended account remains signed in. Repeat sign-out/removal verification as appropriate. Site authentication, MFA, browser security features and visible login UX cannot be established by the cookie fixture. Firefox automatic launches remain headless, so no visible Firefox sign-in workflow is claimed supported.


Profile evidence in this workspace: full kept/temporary/idle/contention/cookie fixtures passed against actual installed Edge and Chrome and official unmodified Firefox 144.0 from WSL2; the full Edge fixture also passed from a native Windows Pi host. Deliberately terminating the worker also closed its browser child on these hosts, so those runs verified dead-owner recovery rather than a surviving live orphan. Live-profile contention was refused; the surviving-orphan fixture branch asserts refusal when that process state is observed, but no surviving orphan was observed in these runs. A focused Edge temporary-crash fixture verified safe cleanup of the recorded dead temporary profile on the next launch. The native Firefox endpoint fixture verified pre-existing tab discovery, cookie sharing, no owned profile creation and preservation of existing/new tabs and the external process. Real interactive account sign-in remains a manual release check.

Browser key aliases are canonicalized before page dispatch, dialog handling, history navigation and the existing browser-window shortcut refusal set. `return`, `del`, `pgup`/`pgdn` and lowercase `arrow*` match their named keys. The local browser-actions fixture checks actual DOM key outcomes, prompt acceptance through `return`, and alias/case forms of existing refused shortcuts without changing foreground/tab state. This preserves the reference refusal policy; it does not newly forbid page key combinations or claim native browser-window shortcuts are supported.
